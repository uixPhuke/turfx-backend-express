# Performance and reliability assessment

PostgreSQL is the source of truth. Current schema includes user/venue relations, booking/resource lookup indexes, conversation timestamp/id pagination, outbox processed/available indexes and push status/available indexes. GiST exclusions and row/serializable locks protect correctness under contention. Existing isolated concurrency tests pass; they are not sustained throughput benchmarks.

API/worker Prisma pools default to five connections each; no connection per request. Readiness checks depend on PostgreSQL and Redis and bound response wait. Redis rate limiting and Socket.IO fanout support replicas, but actual capacity must be measured against the chosen plan. Mobile chat uses websocket-only transport, reconnects up to five times, reauthenticates/rejoins on connection and falls back to 20-second reads when disconnected. Persisted messages and client IDs prevent relying on socket delivery as storage.

Worker iterations do not overlap within a process. Database outbox locking and push leases coordinate workers. Failed stages are logged independently, hold expiry is idempotent, external reconciliation uses stable identifiers, and ambiguous payments remain visible to operators. A process restart can interrupt an external request; recovery must reconcile provider state before reissuing financial work. Provider timeouts are bounded; no blanket write retry is added.

Cloudinary limits dimensions to 2000x2000 and applies automatic format/quality. Private API responses use no-store; image CDN caching is handled by the image provider. Mobile production export compiles Hermes/native bundles and static web routes. Latest measured unsigned outputs: approximately 5.83MB each Android/iOS and 3.07MB web JS, 42 routes. These are bundle file sizes, not installed app size, network gzip size or peak memory. No invented memory/latency/throughput figures are provided.

Before scaling: stage realistic catalog/chat/booking data, record p50/p95/p99 latency, pool wait/errors, DB CPU/locks, RSS/event-loop delay, Redis memory and worker backlog. Exercise concurrent hot-resource booking, reconnect storms and provider timeout scenarios. Define a measured capacity target and error budget; start with one API/worker rather than claiming unmeasured horizontal scalability. Add query indexes only from observed plans. Preserve an admin/migration connection reserve and never disable booking constraints for performance.
